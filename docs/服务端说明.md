# 服务端说明（参考实现，零依赖）

## 1. 它解决什么问题

纯本地原型（`index.html` + IndexedDB）有三条硬伤，写在 README 的「局限与边界」里：

| 硬伤 | 本服务端怎么解决 |
| --- | --- |
| 身份靠顶部下拉手动切换，不是真实凭证 | **真实登录**：口令经 scrypt 加盐哈希存储，登录签发 HMAC 签名 token，服务端每次请求验签 |
| 可见范围只在前端过滤，改前端代码即可绕过 | **文档在出网前按身份过滤**：越权文档根本不下发；直接按 id 请求越权文档返回 **403** |
| 审计存本机 IndexedDB，用户可自行清空 | **服务端 append-only JSONL + 哈希链**：不提供任何修改 / 删除接口，篡改会被 `verifyChain()` 检出并定位到行 |

前端保留纯本地模式作为默认，服务端是**可选增强**——`index.html` 双击就能跑，不受影响。

## 2. 启动

```bash
node server/server.mjs
# 企业内部知识问答与制度助手 · 服务端已启动
#   地址        http://127.0.0.1:8787
```

浏览器打开 `http://127.0.0.1:8787` → 「资料与权限」页 → **服务端模式（可选）** → 填地址、用户名、口令 → 「连接并登录」。

演示账号（首次启动写入 `data/users.json`）：

| 用户名 | 口令 | 角色 | 可见范围 |
| --- | --- | --- | --- |
| `employee` | `demo1234` | 员工 | 所有员工（3 份） |
| `hr` | `demo1234` | 人事 | 所有员工 + 人事专属（4 份） |
| `manager` | `demo1234` | 主管 | 所有员工 + 主管专属（4 份） |
| `admin` | `demo1234` | 管理员 | 全部（5 份） |

环境变量：

| 变量 | 默认 | 说明 |
| --- | --- | --- |
| `ZHIGUI_PORT` / `PORT` | `8787` | 监听端口 |
| `ZHIGUI_HOST` | `127.0.0.1` | 监听地址，默认只绑本机 |
| `ZHIGUI_DATA_DIR` | `<项目根>/data` | 数据目录 |
| `ZHIGUI_SECRET` | 自动生成 | token 签名密钥；未设置则生成并写入 `<data>/secret.key`（权限 0600） |
| `ZHIGUI_CORS_ORIGIN` | 空（只允许同源） | 允许的跨域来源；**必须显式设置**才会下发 CORS 头 |
| `ZHIGUI_TRUST_PROXY` | 关闭 | 设 `1` 才读 `X-Forwarded-For` / `X-Real-IP`；仅部署在反向代理后时开启 |
| `ZHIGUI_TOKEN_TTL_MINUTES` | `120` | token 有效期 |

> 生产部署必须显式设置 `ZHIGUI_SECRET`（否则密钥随数据目录走），并在前面加 TLS 终止。
> 跨域默认关闭；确实需要跨域时把 `ZHIGUI_CORS_ORIGIN` 设成具体来源，**不要用 `*`**。

## 4. 接口

除 `/api/login` 与 `/api/health` 外，其余接口都要求 `Authorization: Bearer <token>`。

| 方法 | 路径 | 权限 | 说明 |
| --- | --- | --- | --- |
| `GET` | `/api/health` | 公开 | 存活探测，返回文档 / 用户 / 审计条数与来源统计 `auditSources` |
| `POST` | `/api/login` | 公开 | `{username, password}` → `{token, expiresAt, user}`；失败 401，限速 429 |
| `GET` | `/api/session` | 登录 | 当前身份 |
| `GET` | `/api/documents` | 登录 | **只返回该身份可见的文档**，附 `total` / `visible` |
| `GET` | `/api/documents/:id` | 登录 | 有权 200；无权 **403** 并由服务端权威记审计；不存在 404 |
| `POST` | `/api/documents` | **仅管理员** | 新增 / 修改文档；非管理员 403 并留痕 |
| `PATCH` | `/api/documents` | **仅管理员** | `{id}` 切换启停 |
| `DELETE` | `/api/documents/:id` | **仅管理员** | 移除文档 |
| `POST` | `/api/events` | 登录 | 上报**白名单内**的纯前端事件；落盘标记 `source=client`；同用户 1 分钟限 60 条，超限 429 |
| `GET` | `/api/audit?limit=` | **仅管理员** | 审计条目 + 哈希链完整性校验结果 + 来源统计 `sources` |

错误响应统一为 `{ "error": "可读中文说明" }`。

## 5. 认证设计

**口令**：`scryptSync(password, salt, 32)`，salt 为 16 字节随机数，`timingSafeEqual` 比对。用户不存在时也做一次等价开销的哈希，避免通过响应时间枚举用户名。登录失败按 IP 限速（5 分钟 10 次）。

**IP 从哪来**：默认只取 socket 地址，**不信任** `X-Forwarded-For` —— 否则客户端可以自己伪造这个头来绕过登录限速、并往审计里写假 IP。只有确实部署在反向代理之后，才设 `ZHIGUI_TRUST_PROXY=1`，此时取 `X-Forwarded-For` 的**最左侧**地址（最初的客户端；右侧是逐跳追加的代理地址，不可信）。测试里有一条专门伪造 `X-Forwarded-For` 并断言审计 IP 未被污染。

**token**：`base64url(payload) + "." + base64url(HMAC-SHA256(payload, secret))`，payload 为 `{sub, role, iat, exp}`。

没有引入 JWT 库，原因有三：本参考实现坚持零依赖；这里只需要「服务端签发、服务端验签」；以及**不引入 `alg` 协商就没有 `alg=none` 这类经典坑**。验签用 `timingSafeEqual`，任何异常一律返回 401。

> 注意：角色是写在 token payload 里的。这意味着**改角色需要重新登录**（本实现如此），但也意味着 token 在有效期内无法被服务端单方面降权。真实系统应引入短时效 access token + refresh token，或在服务端维护会话表以支持即时吊销。

## 6. 权限模型

`policy.mjs` 是单一事实来源：

```js
employee: ["all"]
hr:       ["all", "hr"]
manager:  ["all", "manager"]
admin:    ["all", "hr", "manager"]
```

两处强制点：

1. **读**：`GET /api/documents` 用 `visibleDocuments(role, documents)` 过滤后才序列化。越权文档的**任何字段**都不出现在响应里（测试有专门断言）。
2. **写**：`POST` / `PATCH` / `DELETE` 都要求 `role === "admin"`，否则 403 并记 `denied`。

前端 `index.html` 里有一份语义相同的 `ACCESS_POLICY`，但它的作用已经退化为**渲染与提示**——真正的判定在服务端，前端被改也拿不到数据。

## 7. 审计与哈希链

每条记录：

```jsonc
{
  "seq": 12,
  "at": "2026-10-09T09:31:02.114Z",
  "user": "hr", "role": "hr", "ip": "127.0.0.1",
  "action": "open_document",
  "target": "入职手续办理清单（演示）",
  "detail": "身份「员工」没有查看该文档的权限（该文档可见范围：人事专属）。",
  "result": "denied",
  "prevHash": "a5f2b296…", "hash": "1a85f472…"
}
```

```
hash = sha256(`${prevHash}|${seq}|${at}|${user}|${role}|${action}|${target}|${detail}|${result}|${source}`)
```

首条 `prevHash = "GENESIS"`。`verifyChain()` **每次从磁盘重新读取**再逐条重算——只有读盘重算才能发现「有人直接改了 `audit.jsonl`」，用内存缓存会把篡改掩盖掉（这一点在实现时踩过一次）。

能检出的三类篡改：

| 篡改方式 | 检出理由 |
| --- | --- |
| 改写某条内容 | 该条 `hash` 与重算结果不一致 |
| 删除或插入某条 | 后续记录的 `prevHash` 链不上，或 `seq` 不连续 |
| 换序 | 同上 |

**它不能做什么**：有文件写权限的人可以重算整条链。哈希链只能**发现**篡改，不能**阻止**。生产环境应把日志实时推送到独立的只写存储（对象存储 WORM、日志服务、SIEM），或对链尾定期做外部签名 / 时间戳锚定。

**客户端能伪造什么**：`POST /api/events` 的 `action` / `target` / `detail` 由客户端提供，所以业务事件的内容不可全信。但 `at` / `user` / `role` / `ip` 由服务端补全（测试有断言验证客户端无法伪造 `user`），且**与授权直接相关的动作（登录、打开文档、文档维护）全部由服务端自己记录**，不经过客户端上报。前端也据此跳过重复上报（`SERVER_AUTHORITATIVE` 集合）。

为了让「客户端声明」在**存储层**就与权威记录可区分，`/api/events` 加了三道约束：

| 约束 | 作用 |
| --- | --- |
| **动作白名单** | 只接受前端会主动上报的 9 类纯前端事件：`query` / `query_blocked` / `copy_text` / `llm_config` / `llm_models` / `role_switch` / `export_backup` / `audit_export` / `audit_clear`。`open_document`、`import_document`、`edit_document`、`toggle_document`、`delete_document` 这些**服务端自己会权威记录**的动作一律拒收（400），避免同一件事出现两条来源不同、可信度不同的记录。被拒请求本身也由服务端权威留痕（`client_event_rejected` / `denied`）。<br>白名单必须 ⊇ 前端 `AUDIT_LABELS` 减去 `SERVER_AUTHORITATIVE` —— **少放行一个动作，它就会被 400 拒掉并记成「被拒事件」，等于审计静默降级**。这个不变量由 `server-mode-test` 的一致性用例守护。 |
| **来源标记** | 白名单事件落盘写 `source=client`；服务端自己产生的记录写 `source=server`。`source` **参与哈希链计算**，取证时一眼可分「服务端确认发生」与「客户端声称发生」。`/api/audit` 与 `/api/health` 都返回 `{ server, client }` 计数。 |
| **写入限速** | 同一用户 1 分钟最多 60 条，超限返回 429 并留痕。在没有日志轮转机制之前，这是防止审计文件被高频上报灌爆的兜底。 |

这三道约束把 `/api/events` 从「客户端可以往里写任何东西」收窄为「客户端只能声明有限的几类纯前端行为，且这些声明永远带 `source=client` 标记」。换句话说，**哈希链保证完整性（有没有被改动），`source` 标记保证可追溯性（记录的事情是谁声称的）** —— 两者合起来才谈得上审计可信度。

## 8. 静态资源隔离与安全响应头

服务端**只托管 `index.html`**：

- `GET /` 与 `/index.html` → 返回页面
- 其它非 `/api` 路径 → 一律 **404**

这样探测 `/data/audit.jsonl`、`/data/secret.key`、`/server/server.mjs` 时既拿不到内容，也拿不到「该路径存在」的信号。测试里三条都有断言。

所有响应（静态页面与 API）统一带这几个头：

| 头 | 值 | 作用 |
| --- | --- | --- |
| `X-Content-Type-Options` | `nosniff` | 禁止浏览器嗅探 MIME，避免把上传内容当脚本执行 |
| `X-Frame-Options` | `DENY` | 禁止被 iframe 嵌套（点击劫持） |
| `Referrer-Policy` | `no-referrer` | 不向外部泄露来源路径 |
| `Content-Security-Policy` | 见下 | 纵深防御 |

CSP 的取值：

```
default-src 'self'; script-src 'self' 'unsafe-inline'; style-src 'self' 'unsafe-inline';
img-src 'self' data: blob:; connect-src *; object-src 'none'; base-uri 'none';
frame-ancestors 'none'; form-action 'none'
```

**要诚实说明 `'unsafe-inline'`**：本应用是单文件设计，样式与脚本都内联在 `index.html` 里，所以 `script-src` / `style-src` 必须放行内联 —— 这等于放弃了 CSP 对 XSS 的主要防护。这是「双击即用」的直接代价，不是疏忽。即便如此，其余指令仍然挡得住外链脚本、`<object>` 嵌入、被 iframe 嵌套与 `<base>` 劫持。

`connect-src *` 同样是必要的：生成式回答要直连用户自己配置的模型服务，来源不可预知。若部署时不需要该功能，可以把它收紧为具体域名。

**跨域默认关闭**：只有设置了 `ZHIGUI_CORS_ORIGIN` 才会下发 `Access-Control-Allow-*` 头，并附带 `Vary: Origin`。默认（不设）时浏览器同源策略自然生效，跨站页面拿不到任何响应。

## 9. 一个刻意的取舍：检索没有下沉

README 的后续计划写的是「前端只保留展示」。本实现只把**权限与审计**下沉了，检索仍在前端执行——但跑在**服务端下发的文档集**上。

理由：授权在数据下发那一刻就已经完成，检索只是对**已授权数据**做纯计算，不产生新的越权面。而把检索算法搬到服务端意味着要么复制一份实现（两份代码必然漂移），要么把单文件应用拆成模块（破坏「双击即用」）。权衡下来，保持一份检索实现、让服务端负责授权边界，是更稳的选择。

代价也要说清楚：**服务端无法对「检索行为本身」做审计与限流**（比如「这个人在 5 分钟内问了两千次」）。要做到那一步，需要把检索也搬到服务端，或者至少把「问句 + 命中的文档 id」在服务端校验一遍。

## 10. 测试

```bash
node eval/server-mode-test.mjs      # 76 项断言
```

测试会**真实拉起一个服务端子进程**（随机端口 + 临时数据目录），跑完自动清理。覆盖：

- 认证：未登录 401、错误口令 401、不存在用户名 401、伪造签名段 401、伪造 payload 提权 401、正确登录签发 token
- 权限：四个角色各自的可见份数、越权文档不出网、403 响应不含正文、有权文档 200
- 写入 RBAC：非管理员新增 / 启停 / 移除全部 403，管理员成功
- 审计：非管理员读 403、管理员读 200、哈希链完整、越权记为 denied、带 user/role/ip、**直接改写 audit.jsonl 被检出并定位到第 2 行**、还原后恢复完整
- 上报约束：白名单事件被接受（202）且标记 `source=client`、非白名单事件 400 且权威留痕 `client_event_rejected` / `denied`、权威记录带 `source=server`、审计接口返回来源统计、**同用户 1 分钟超 60 条被限速 429**、**白名单与前端动作表一致性（防漂移）**
- 静态隔离：`/data/*` 与 `/server/*` 均 404
- 安全加固：静态页与 API 均带 `nosniff` / `X-Frame-Options: DENY` / CSP；**默认不下发 CORS 头**；**伪造 `X-Forwarded-For` 不污染审计 IP**
- 前端集成：默认本地模式、登录后进入服务端模式、身份下拉锁定、文档集来自服务端且无受限卡片、检索正常作答、非管理员读服务端审计被拒、断开后回到本地 5 份文档、管理员可看服务端审计且含哈希链完整性

## 11. 上线前还需要什么

| 项 | 现状 | 生产要求 |
| --- | --- | --- |
| 传输加密 | HTTP 明文 | TLS 终止（Nginx / 网关），强制 HTTPS |
| token 存储 | 前端 `sessionStorage` | 改 httpOnly + Secure + SameSite Cookie，配 CSRF 防护 |
| token 吊销 | 不支持，过期前一直有效 | 服务端会话表 / 短时效 access + refresh |
| 口令策略 | 固定演示口令 | 强口令 + 失败锁定 + 可选 MFA |
| 审计落地 | 本地 JSONL | 只写存储 / 日志服务 + 链尾外部锚定 |
| 文档存储 | 单机 JSON 文件 | 数据库 + 文件对象存储，事务与并发控制 |
| 检索审计 | 无（检索在前端） | 检索下沉到服务端或至少回传命中 id 校验 |
| 加密 | 无 | 静态加密（磁盘 / 字段级）、备份恢复演练 |
