# 文档解析说明（DOCX / PDF，零依赖）

## 1. 为什么不用 pdf.js / mammoth

主流方案是引入 `pdf.js` 与 `mammoth`。本项目刻意没有采用，原因有三条：

| 约束 | 说明 |
| --- | --- |
| **单文件形态** | 整个应用就是一个 `index.html`，双击即用。引入外部库要么内联进 HTML（体积暴涨、难维护），要么退回多文件 + 构建步骤，与「零构建、可离线」的定位冲突 |
| **文件不出本机** | 解析全程在浏览器内存里完成，文件**不上传任何服务器**。引入 CDN 版库会引入外链依赖与供应链风险 |
| **能力边界可接受** | 企业内部制度文档多是「标题 + 段落」结构，需要的是**文本与层级**，不是像素级还原排版 |

因此实现路线是：**用浏览器原生 API 手写最小可用的解析器**。核心依赖只有三个平台能力：

- `DecompressionStream("deflate-raw")` / `DecompressionStream("deflate")` —— 原生解压
- `TextDecoder` —— 字节到字符串（`utf-8` / `latin1`）
- `DOMParser` —— HTML 导入时去标签

## 2. 支持范围

| 扩展名 | 上限 | 解析方式 |
| --- | ---: | --- |
| `txt` / `md` / `markdown` / `csv` / `json` | 1 MB | `FileReader.readAsText(file, "UTF-8")` 直读 |
| `html` / `htm` | 1 MB | `DOMParser` 解析后移除 `script/style/noscript`，取 `body.textContent` |
| `docx` | 8 MB | ZIP 中央目录 → `word/document.xml` → 段落/标题 → Markdown |
| `pdf` | 8 MB | 扫描内容流 → FlateDecode → ToUnicode CMap → 文本操作符 |

其余扩展名一律拒绝并提示 `当前支持 TXT、Markdown、CSV、JSON、HTML、DOCX、PDF`。

导入后的标题取文件名（去扩展名），正文回填到编辑框，用户可再手工修改后保存。

## 3. DOCX 解析

### 3.1 原理

DOCX 是一个 ZIP 包，正文在 `word/document.xml`。流程：

```
ArrayBuffer
  → readZipDirectory()  找 EOCD(0x06054b50) → 中央目录(0x02014b50) → 本地头(0x04034b50)
  → 取 word/document.xml 的 { method, compressedSize, dataStart }
  → method === 0 ? 直接读 : inflate(raw, "deflate-raw")
  → docxXmlToMarkdown()
```

`readZipDirectory` 的实现要点：

- **EOCD 从尾部倒着找**：`0x06054b50` 之后可能跟 ZIP 注释，所以从 `length - 22` 往前搜，最多回退 64 KB
- **偏移全部走中央目录**：本地文件头的 `extra field` 长度可能和中央目录不一致，因此数据起点按**本地头**的 name/extra 长度算，条目信息按**中央目录**读
- **不信任压缩前大小**：只用 `compressedSize` 截取数据，解压后长度由 `DecompressionStream` 决定

### 3.2 段落与标题

`docxXmlToMarkdown` 按 `<w:p` 切段落，每段内：

| 提取项 | 来源 |
| --- | --- |
| 文本 | 全部 `<w:t>` 内容拼接（XML 实体解码：`&lt;` `&gt;` `&amp;` `&quot;` `&apos;` `&#N;`） |
| 标题层级 | `<w:pStyle w:val="…">`，匹配 `Heading1`~`Heading9` 或 `标题 1`~`标题 9` |

标题输出为 `#` × 层级 + 文本，其余段落原样输出；空段落保留为换行（连续 3 个以上换行压成 2 个）。

**为什么标题很重要**：标题会进入 `buildSections` 的 `headingTitle`，进而参与标题权重打分与编号小节聚合——也就是说，DOCX 里的 `1.1 差旅报销要求` 导入后能像 Markdown 文档一样被「按序号定位」和「标题匹配」命中。

### 3.3 不提取的内容

表格（`w:tbl`）、图片、批注、页眉页脚、脚注、文本框。原因：这些结构在检索语境下收益低，而正确还原的成本高（表格需要重建行列、图片需要 OCR）。表格单元格里的 `<w:t>` 目前会**按段落顺序线性输出**，内容不丢但结构丢失。

## 4. PDF 解析

### 4.1 原理

PDF 的文本不是明文，而是「内容流里的字形码 + 字体字典里的映射表」。流程：

```
Uint8Array → latin1 字符串（保留字节与字符一一对应）
  → 正则扫描 stream\r?\n … endstream
  → 回溯找 << … >> 字典，看是否含 FlateDecode
  → FlateDecode 的用 inflate(raw, "deflate")，其余原样 latin1
  → 从所有解压结果里收集 ToUnicode CMap
  → extractPdfStrings()：按文本操作符切分并映射字形码
```

### 4.2 ToUnicode CMap

`parsePdfCMap` 解析两类块：

| 块 | 含义 | 处理 |
| --- | --- | --- |
| `beginbfchar … endbfchar` | 单字符映射 | `<字形码> <Unicode 十六进制>` 逐个入表 |
| `beginbfrange … endbfrange` | 区间映射 | `<起> <止> <目标>`，逐码递增；区间跨度 > 65535 时跳过（防异常文件撑爆内存） |

`hexToText` 按每 4 位十六进制 = 1 个 UTF-16 码元拼接，因此中文（BMP 内）可以正确还原。多个内容流各自带 CMap 时，**先入表者优先**（`if (!cmap.has(key))`），避免后出现的子集字体覆盖主映射。

### 4.3 文本操作符

`extractPdfStrings` 只取三类 token：

| token | 含义 | 处理 |
| --- | --- | --- |
| `(…)` | 字面量字符串 | 反转义 `\n \r \t \b \f \( \) \\ \ddd(八进制)` |
| `<…>` | 十六进制字符串 | 经 CMap 映射；未命中映射的码位，若落在可打印 ASCII（32~126）则按 ASCII 输出 |
| `Td` / `TD` / `T*` / `ET` | 换行 / 定位 / 结束文本对象 | 输出 `\n` |

`Tj` / `TJ` 本身不需要处理——它们只是「把栈上的字符串画出来」，字符串已经在 token 流里被捕获。行序由 `Td/TD/T*` 划分，不做坐标重排（双栏排版可能串行，属于已知边界）。

### 4.4 可读率校验（关键防线）

PDF 解析最容易出的问题不是报错，而是**静默产出乱码**：扫描件、加密文档、用了自定义编码且没有 ToUnicode 表的字体，都会解出一堆无意义字符。如果直接写进知识库，检索会被污染且很难排查。

因此解析后必须过两道校验：

```js
if (text.replace(/\s/g, "").length < 20 || readableRatio(text) < 0.5) → 拒绝导入
```

`readableRatio` 统计「中日韩汉字 + 中文标点 + 全角字符 + 字母数字 + 常用中文标点 + 空白」占全部字符的比例。

不通过时报：

> 该 PDF 未提取到足够的可读文本（可能是扫描件、加密文档或使用了特殊字体编码），建议先转成文本再导入

并且**不回填正文**，用户不会把乱码存进库。DOCX 侧同理，提取结果为空时报「未能从该 DOCX 中提取到文本，请确认文件未加密或受保护」。

## 5. 与检索层的衔接

解析产出的是**纯文本（DOCX 带 Markdown 标题）**，之后走的是完全相同的管线：

```
解析文本 → buildSections（标题切分 / 编号祖先识别 / 【追问N】分组）
        → scorePassage（正文 + 标题权重）
        → 编号小节聚合 → 排序取用 → 回答 + 来源标注
```

因此导入一份带 `1.1` / `1.2` 编号的 DOCX 或 PDF 后，可以直接用「追问 1」这样的序号提问，行为与内置 Markdown 语料一致。

## 7. 已知边界

- **表格 / 图片不解析**：DOCX 表格内容线性输出、结构丢失；PDF 内嵌图片完全忽略
- **扫描件不支持**：需要 OCR，本项目不做，明确拒绝并提示先转文本
- **PDF 双栏排版可能串行**：不做基于坐标的文本重排
- **加密文档**：加密的 DOCX（`EncryptedPackage`）与带密码的 PDF 都会解析失败或触发可读率校验，给出提示而非静默失败
- **解析在主线程**：8 MB 上限就是为此设定的经验值，超过这个量级应放到 Web Worker
- **不保证版式还原**：目标是「拿到可检索的文本与标题层级」，不是「复刻排版」
